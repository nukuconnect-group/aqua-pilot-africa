
- AquaAssistant UI must remain in `AquaAssistantModule`; the legacy `AquaAssistant` widget is not a second implementation. This keeps one mounted assistant surface and one persisted conversation system.
- Dashboard keeps one assistant instance outside the keyed module subtree, with explicit page/floating presentation; switching entry paths preserves its conversation and input.
- AssistantOverview reads existing unit-scoped sources without creating alerts/default thresholds; aqua-assistant verifies the historical app session and builds read-only context from accessible unit IDs, distinguishing absent data and recorded measurements from estimates.
- App owns one QueryClientProvider with focus refetch disabled; account/unit keyed queries share cache without remounting forms.
- CommercialPerformance and ReportsManagement share account/unit data via useCommercialData; commercialReports adapts the shared reports layout and exports. CommercialCharts renders plots; analyticsDateRange/analyticsValues validate dates/numbers; forecasts use complete months.
- Infrastructure depreciation uses the existing specifications configuration and depreciationAssetId, synchronized atomically by the invoker trigger in docs/sql/infrastructure_depreciation.sql on the historical app backend; unchanged configuration must not overwrite accounting edits.
- Infrastructure QR generation is centralized in infrastructureQr: persisted unit/infrastructure IDs remain stable, current name/type and saved specifications.number enrich the payload; never invent a number or expose other specifications. Cycle IDs resolve uniquely within the same unit so cards and exports share one identity without schema changes.
- Feeding print/PDF windows use printWhenReady to wait for assets and rendered SVG layout instead of printing immediately or after a fixed delay.
- Render the assistant launcher through a body portal independently of module eligibility, hiding it only while the assistant overlay is actually rendered; keep the conversation permission check so layout clipping or stale open state cannot hide the launcher or bypass access rules.
- Centralize universal AquaAssistant eligibility in core/always-open module rules and exempt only its screen from subscription expiry; keep authenticated server calls and unit data permissions unchanged.
- Preserve explicit tab IDs during URL resolution; permission-group IDs must not redirect sibling screens, so Stock remains a separate screen with existing feeding permissions.

- Treasury uses append-only unit-scoped movements with server-side account locking and balanced journal lines; account opening is atomic to prevent partial initialization.
- Business sale cancellation preserves the sale and its previous status; journal generation retains original entries and adds dated reversals, while linked POS cash refunds are atomic with cancellation.
- Accounting and treasury use the same application client as sales; deployment must target the application's actual backend, never silently switch existing users to another database.
- CRM contact shortcuts share ContactActions and open the user's messaging applications; they do not send messages automatically.
- POS uses the active unit's real stock and sale items through posCatalog; purchase cost is never used as a selling price.
- Cash sale history is linked through cash_movements.sale_id and session_id, including closed sessions, to avoid duplicating sales records.
- POS retains the sale and its original cash session when a cash posting fails; retry the posting rather than create a second sale.
- POS checks that the selected cash session is still open before recording a sale and reports unexpected failures; this client check does not replace server-side atomic posting.
- Stock removals use one unit-scoped selected-ID delete and a confirmation; reset snapshots the unit's displayed IDs rather than issuing an unbounded delete, preserving existing movement and financial history.
- Stock items carry an explicit purpose (production or commercial, src/lib/stockPurpose.ts); only commercial, in-stock items reach the POS and only production items feed fish, so inputs are never sold by name or category.
- Unit-specific stock presentation and creation/import purpose use the shared stockPurpose policy; filter without reclassifying existing items to preserve inventory history. Mandatory module restrictions remain centralized in planModules so stale configuration cannot restore excluded screens.
- A global DOM guard (src/lib/domPatch.ts) tolerates external DOM moves (browser translation) so React no longer crashes on insertBefore/removeChild.
- Unit = warehouse: a completed production cycle's harvest is transferred once (ref in notes) into the same unit's commercial stock; POS posts the cash movement and commercial stock deduction in one server function (pos_post_sale), idempotent per sale; the client path is only a fallback for databases without it.
- AI POS suggestions run in the pos-ai-suggest function, which verifies the app-backend user and only returns real catalog items; the seller confirms before anything enters the cart.
- AquaHealth calls its deployed Cloud function with the existing application session; the function validates that session against the application backend and gates photo diagnoses on explicit real-fish recognition, keeping species searches separate.
- Cash registers (cash_sessions) are created by the unit owner, who assigns team members via cashier_ids; RLS lets only the owner and assigned cashiers read registers and post movements, and a trigger prevents non-owners from changing the assignment.
- POS sales are mirrored once into treasury by payment method (cash/Mobile Money → unit cash account, card/transfer → unit bank account) with counterpart 411, since the server validator rejects class-5 counterparts; past sales are backfilled idempotently by sale id. Register handovers are cash history only; register-to-register transfers never touch treasury.
- Reopening a closed register goes through public.reopen_cash_register (docs/sql/reopen_cash_register.sql): a new session copies name, unit and cashier_ids with the counted balance, so assigned cashiers keep access until removed.
- Treasury accounts are never auto-created; owners create them per unit and may move one to another of their units via public.reattach_treasury_account (docs/sql/treasury_bank_reattach.sql), which moves its history but refuses accounts with transfers. Inter-unit transfers go through public.transfer_between_units (docs/sql/treasury_inter_unit_transfer.sql): two atomic movements via liaison account 185, owner only.
- Offline support: the service worker is generated by vite-plugin-pwa (generateSW) and registered only by src/lib/pwaRegister.ts, which refuses dev/preview hosts and ?sw=off; never hand-write public/sw.js or a second registration. Updates install in the background without forced page reloads.
- Service worker controller changes must never force a page reload, even in hidden tabs, because backgrounding does not imply saved forms; the next user-initiated reopening loads the new shell.
- PWA updates have one guarded registrar, hourly background checks, no mounted-screen activation, and a waiting worker until existing pages close; navigations use NetworkFirst. Slow loading and orphaned body locks must never trigger a module remount because they do not establish a crash.
- Auth profile/role read failures preserve an already mounted account; transient session events are not sign-outs. Never fabricate offline authentication or infer server privileges from local storage.
- Feeding forms persist account/unit/tab-scoped drafts with useSessionDraft and clear them only after successful saves; this protects edits against module recovery remounts.
- The historical application database is writable from the sandbox via the AQUAPILOTE_DB_URL secret (psql); install prepared SQL there directly instead of asking the user. public.record_sheet_feeding is installed there (docs/sql/record_sheet_feeding_legacy.sql) and makes sheet feeding atomic server-side; the client path is only a fallback for databases without it.
- feeding_records.infrastructure_id has an FK to cycle_infrastructures, not unit_infrastructures; feeding_sheets and the client hold unit-infrastructure IDs, so both the server function and the client fallback resolve a same-named active cycle_infrastructure for the record (NULL when none). This base has no pg_net under extensions: the stock-alert trigger calls net.http_post, never extensions.net.http_post.
- Per-period plans (time + quantity) live in a marker at the end of feeding_sheets.observations (src/lib/feedingSheetPlan.ts) since that backend lacks period_times/infrastructure_ids.
- Feeding sheet creation/editing validates exactly one unit-owned infrastructure, saved in infrastructure_id, and refuses overlapping active date ranges; legacy sheets without one are attached explicitly in the feeding dialog, never silently.
- Feeding programs use existing start_date/end_date/days and optional weekday plans in the observations marker; daily sheets read unit/infrastructure/date-scoped records and exports use the selected date, so periods accumulate without duplicating programs or requiring unavailable schema columns.
- AquaHealth PDF reports (src/lib/healthReportPdf.ts) embed the analyzed fish photo when available and a consultant block; the PDF builder is async because images are loaded and converted to JPEG.
- Unit eligibility uses date-aware subscriptionAccess and unitTypeAccess: an active trial bypasses type restrictions, paid subscriptions use profiles.production_units, and expiry suspends unit screens without deleting data; preserve admin exceptions and legacy empty-list behavior. Server enforcement must target the historical application backend, not the unrelated managed database.
- Periodic/focus refreshes (subscription, plan rules, stock lists) must not toggle loading states after the first load, because guards render a loader in place of the module and would unmount open forms; the stock add form also keeps its draft with useSessionDraft.
